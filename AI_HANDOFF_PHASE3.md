## Project Purpose

The CITY Électronique ecommerce platform is an omni-channel, commercial e-commerce solution engineered specifically for **CITY Électronique**, a premier consumer electronics and home appliance retailer based in Casablanca, Morocco.

Key operational characteristics of the retailer:
* **Physical Showroom:** Rue Jean Jaurès, Quartier Maârif, Casablanca.
* **Central Warehouse & Distribution:** Zone Industrielle Aïn Sebaâ, Casablanca.
* **Moroccan Commercial Context:** Moroccan Dirham currency (`MAD` / `DH`), French and Arabic editorial metadata, WhatsApp-driven checkout tailored to Moroccan consumer buying behavior, multi-location stock derivation, and supplier feed synchronization (e.g., official Moroccan tech distributors).

## Database

### Technology & ORM
* **Database Engine:** PostgreSQL
* **ORM:** Drizzle ORM (`drizzle-orm`) with schema migrations managed via `drizzle-kit`.
* **Configuration:** `drizzle.config.ts` targeting `./lib/db/schema.ts` with SQL migrations output to `./drizzle`.

### Schema & Important Tables (17 Tables)
1. `categories`: Hierarchical product taxonomy with Moroccan slugging.
2. `brands`: Official manufacturer and distributor brands (Apple, Sony, Samsung, etc.).
3. `products`: Canonical product entities with title, slug, brand, category, editorial description, SEO metadata, and published status.
4. `product_variants`: SKU-level variants with specific attributes (color, storage, connectivity).
5. `product_images`: Media assets with resolution, primary flag, and verification status (`pending`, `verified`, `rejected`).
6. `product_specifications`: Key-value technical specifications.
7. `inventory_locations`: Physical locations (`Showroom Maârif`, `Dépôt Central Aïn Sebaâ`).
8. `inventory_levels`: Physical quantity and reserved quantity per variant and location.
9. `inventory_movements`: Historical stock adjustments and transfer logs.
10. `suppliers`: Registered external suppliers and distributor partners.
11. `supplier_feeds`: Feed configurations (CSV, JSON, scheduled sync parameters).
12. `catalog_imports`: Import batch execution records with snapshot status and safety metrics.
13. `import_diff_items`: Granular staged changes (action, before/after snapshots, safety flags).
14. `orders`: Order records with customer contact, shipping address, and Moroccan payment method.
15. `order_items`: Order line items capturing quantity and unit prices.
16. `order_snapshots`: Immutable JSON freeze of product name, variant attributes, price, and warranty at time of purchase.
17. `audit_logs`: Immutable security and administrative mutation records.

### Key Relationships
* `products` $\rightarrow$ `categories` (N:1), `brands` (N:1), `product_variants` (1:N), `product_images` (1:N).
* `product_variants` $\rightarrow$ `inventory_levels` (1:N across locations).
* `catalog_imports` $\rightarrow$ `import_diff_items` (1:N).
* `orders` $\rightarrow$ `order_items` (1:N) $\rightarrow$ `order_snapshots` (1:1).

### Storage Distinction: Development/Test vs. Production PostgreSQL
* **Development & Test Environment:** Automated tests and dev sandbox instances utilize `canonicalStore` (`lib/data/store.ts`) and pure domain services. This provides deterministic, sub-second execution without external database dependencies in containerized sandboxes.
* **Production Database:** The 17-table schema in `lib/db/schema.ts` and generated migrations in `drizzle/` represent the live PostgreSQL target. When deploying to production or staging with a live PostgreSQL instance, `DATABASE_URL` connects the Drizzle client directly.

## Authentication & Security

### Admin Sessions & Server-Side Authorization
* **Session Service:** `AdminSessionService` (`lib/auth/session.ts`) provides centralized server-side authentication and session validation.
* **Session Cookie:** Authenticated state is maintained via the `city_admin_session_v3` HTTP cookie containing signed identity properties (`userId`, `role`, `name`, `authenticatedAt`).
* **Endpoint Verification:** Every `/api/admin/*` route executes `await AdminSessionService.verifyPermission(req, requiredPermission)` before returning data or processing mutations.

### RBAC & Role Hierarchy
Defined in `lib/auth/rbac.ts`:
1. **`superadmin`** (Directeur Général CITY):
   * Full access to catalog, inventory, imports, media, and audit trails.
   * **Sole role** authorized to perform Snapshot Safety Guard overrides (`PERMISSIONS.CATALOG_SAFETY_OVERRIDE`).
2. **`admin`** (Responsable Opérations Casablanca):
   * Can create and edit products, set price overrides, adjust inventory, and commit standard imports.
   * **Denied:** Cannot override a blocked safety guard snapshot.
3. **`catalog_manager`** (Gestionnaire Catalogue):
   * Can edit editorial copy, update SEO metadata, and verify media assets.
   * **Denied:** Cannot adjust inventory, cannot commit imports, cannot override safety guards, cannot view sensitive audit logs.

### Production Role-Switching Protection
* In production (`NODE_ENV === 'production'`), arbitrary role elevation via `POST /api/admin/auth/session` is strictly blocked with HTTP 403 Forbidden.
* Client-supplied headers (e.g. `x-admin-role`) are never trusted in production.
* In development/test mode, role switching is restricted to the three valid whitelisted roles.

### Security Boundaries & File Upload Security
* **File Size Ceiling:** 10 MB maximum payload limit (`10 * 1024 * 1024` bytes) enforced in `app/api/admin/imports/route.ts`.
* **File Type Whitelisting:** Restricted strictly to `.csv` and `.json`.
* **Filename Sanitization:** Path traversal patterns (`..`, `/`, `\`) and dangerous characters are stripped.
* **Safe In-Memory Parsing:** Feeds are parsed in memory without dynamic script evaluation or disk execution.

## Catalog

### Products, Variants & Identifiers
* Every product features a title, unique slug, brand, category, editorial description, Moroccan SEO tags, and publication state.
* Products without explicit options automatically provision a default variant.
* **Nullable Identifiers:** SKU and barcode are nullable and not globally mandatory, accommodating Moroccan electronics distributor realities. Model numbers are also supported.

### Ownership Model & Store Overrides
Catalog fields are partitioned into three ownership tiers:
1. **Source-derived:** Attributes provided by external supplier feeds (base cost, supplier title, raw payload).
2. **Store-managed:** Attributes authored by the CITY Électronique editorial team (French descriptions, Moroccan showroom badges, warranty terms, SEO tags).
3. **Manual Overrides:** Explicit overrides applied to fields normally governed by the supplier feed (e.g. `price`, `name`).

### Canonical Display Behavior
* If an item has an active price override (`isPriceOverridden: true`), the display price remains pinned to `overridePrice`.
* Incoming supplier price updates are logged in the diff as `overriddenBlocked: true` and will NOT overwrite the store's price.
* Removing an override (`DELETE /api/admin/products/[id]/override`) deterministically restores the original source-derived price without data loss.

## Import System

### Feed Support & Dry-Run
* Ingests CSV and JSON supplier feeds via file upload or payload.
* Always executes a non-destructive dry run before committing any changes.

### The 6 Diff Actions
1. **`CREATE`**: New supplier records matching no existing catalog identity.
2. **`UPDATE`**: Existing products with modified supplier attributes (protecting active store overrides).
3. **`UNCHANGED`**: Identical supplier data; requires zero database writes.
4. **`DEACTIVATE`**: Active items absent from a validated complete snapshot.
5. **`MANUAL_REVIEW`**: Ambiguous records or collision matches requiring human operator intervention.
6. **`ERROR`**: Corrupted rows, invalid numeric prices, empty mandatory fields, or safety-blocked operations.

### Conservative Identity Matching Hierarchy
Incoming records are matched against existing catalog items in strict priority order:
1. **Priority 1 — Exact Source Record ID:** `sourceCode` + `sourceRecordId`.
2. **Priority 2 — Exact Barcode Match:** Checked if barcode has $\ge 8$ characters. If duplicate barcodes exist in the catalog, triggers collision detection and flags for `manual_review`.
3. **Priority 3 — Exact SKU Match:** Checked if SKU has $\ge 3$ characters. Duplicate collisions flag for `manual_review`.
4. **Priority 4 — Exact Model Number Match:** Normalized alphanumeric match. Duplicate collisions flag for `manual_review`.
5. **Fuzzy Matching Prohibition:** Under no circumstances are records matched by fuzzy text or name similarity.

### Snapshot Safety Guard
* **Threshold:** 15% maximum volume drop on complete snapshots (`isFullSnapshot: true`).
* **Trigger:** If a complete snapshot drops $>15\%$ compared to the previous active baseline, all automatic deactivations are blocked (`report.safety.triggered = true`, `report.safety.blocked = true`).
* **Partial Feeds:** Partial feeds (`isFullSnapshot: false`) never trigger absence deactivations.
* **Superadmin Override:** Unblocking a safety-tripped snapshot requires the `superadmin` role and an explicit reason of at least 10 characters.
* **Idempotency:** Re-running the exact same feed produces 0 creations, 0 deactivations, and 100% `UNCHANGED`.

## Inventory

### Stock Derivation Formula
$$\text{Available Stock} = \max(0, \text{Physical Stock} - \text{Reserved Stock})$$
* **Derived Only:** Available stock is strictly computed dynamically; it is never persisted as an independent writable database field.
* **Non-Negative Guarantee:** Negative available stock is mathematically impossible (`Math.max(0, ...)`).

### Physical Locations
1. **Showroom Casablanca Maârif** (`loc_maarif`, `casa_maarif_showroom`): Retail floor stock available for immediate in-person pickup.
2. **Dépôt Central Aïn Sebaâ** (`loc_ain_sebaa`, `ain_sebaa_depot`): Central fulfillment warehouse.

### Inventory Adjustments & Audit Requirements
* Adjustments support both relative deltas (`+5`, `-2`) and absolute counts (`mode: 'count'`).
* Every stock adjustment mandates an operational reason and logs the executing administrator's ID and name.

## Audit System

### Immutability & Event Structure
* Managed via `AuditService` (`lib/audit/service.ts`).
* Audit records are append-only and cannot be updated or deleted.
* Record schema: `userId`, `adminName`, `action`, `entityType`, `entityId`, `summary`, `details`, `timestamp`.

### Critical Audited Actions
* `product.create`: Product and initial variant creation.
* `product.update`: Editorial or SEO modification.
* `product.override_price`: Manual price override applied.
* `product.remove_override`: Price override deleted and source price restored.
* `inventory.adjust`: Physical stock adjustment with reason.
* `import.dry_run`: Staging of supplier import diff.
* `import.commit`: Application of staged import changes.
* `import.safety_override`: Superadmin unblocking of a snapshot safety violation.
* `image.verify`: Media asset verification status change.

## Phase 3 Security Fixes

During the Phase 3 verification audit, the following security hardening measures were implemented:
1. **Server-Side Session Enforcement:** Migrated administrative endpoints (`/api/admin/*`) from reading unverified client request headers to enforcing authenticated server-side sessions via `AdminSessionService.verifyPermission`.
2. **Production Role Elevation Guard:** Implemented an explicit guard blocking role switching whenever `NODE_ENV === 'production'`.
3. **Import Diff Action Completeness:** Added explicit support for `manual_review` as a first-class action in the Diff Engine and Stored Import records.
4. **File Upload Security:** Added a 10MB payload ceiling, filename path traversal sanitization, and strict file-type whitelisting (`.csv`, `.json`).
5. **Model Number Identity Matching:** Implemented the fourth tier of identity matching for model numbers with duplicate collision detection.
